*# 1. Purpose*



*This document defines the official Issue Template used throughout the Francisco Sánchez Portfolio AI-First engineering ecosystem.*



*An Issue represents a single unit of engineering work that can be planned, implemented, reviewed, tracked, validated, and completed.*



*Every engineering task shall be represented by an Issue before implementation begins.*



*---*



*# 2. Objectives*



*The Issue Template aims to:*



*- Standardize engineering work items.*

*- Improve planning consistency.*

*- Preserve traceability.*

*- Support AI-assisted execution.*

*- Enable predictable workflows.*

*- Improve collaboration.*

*- Facilitate prioritization.*

*- Reduce ambiguity.*



*---*



*# 3. Issue Philosophy*



*An Issue is not merely a task.*



*It is an engineering commitment.*



*Every Issue shall clearly communicate:*



*- What must be done.*

*- Why it must be done.*

*- Who owns it.*

*- When it is considered complete.*



*Issues form the operational backbone of engineering execution.*



*---*



*# 4. When to Create an Issue*



*An Issue shall be created whenever:*



*- A new feature is implemented.*

*- A defect is identified.*

*- Technical debt is addressed.*

*- Documentation is updated.*

*- Infrastructure changes occur.*

*- AI workflows require modification.*

*- Architectural improvements are planned.*



*Minor personal reminders shall not become Issues.*



*---*



*# 5. Standard Structure*



*Every Issue shall include:*



*```*

*Metadata*

*Summary*

*Background*

*Problem Statement*

*Business Value*

*Scope*

*Acceptance Criteria*

*Priority*

*Severity*

*Dependencies*

*Implementation Notes*

*Testing Requirements*

*Definition of Done*

*AI Operational Context*

*References*

*```*



*---*



*# 6. Metadata*



*Minimum metadata shall include:*



*| Field | Description |*

*|--------|-------------|*

*| Issue ID | Unique identifier |*

*| Title | Short descriptive title |*

*| Type | Feature, Bug, Improvement, Documentation, Task, Refactor |*

*| Status | Open, In Progress, Review, Done, Closed |*

*| Priority | Critical, High, Medium, Low |*

*| Owner | Responsible engineer |*

*| Sprint | Assigned sprint |*

*| Labels | Classification tags |*



*Metadata shall support engineering traceability.*



*---*



*# 7. Summary*



*Provide a concise description explaining:*



*- What must be completed.*

*- Expected result.*

*- Overall objective.*



*The summary shall fit within a few sentences.*



*---*



*# 8. Background*



*Describe the context that originated the Issue.*



*Include:*



*- Business context.*

*- Technical context.*

*- Existing behavior.*

*- Historical information if applicable.*



*Background shall help future engineers understand the Issue.*



*---*



*# 9. Problem Statement*



*Describe:*



*- Current problem.*

*- Existing limitations.*

*- Risks.*

*- Desired improvement.*



*The problem shall remain objective and measurable.*



*---*



*# 10. Business Value*



*Explain why the Issue matters.*



*Examples include:*



*- User experience improvement.*

*- Security enhancement.*

*- Performance optimization.*

*- Technical debt reduction.*

*- Developer productivity.*

*- AI capability improvement.*



*Every Issue shall provide engineering value.*



*---*



*# 11. Scope*



*Clearly define:*



*Included work.*



*Excluded work.*



*System boundaries.*



*Expected deliverables.*



*Scope prevents uncontrolled expansion.*



*---*



*# 12. Acceptance Criteria*



*Acceptance Criteria determine completion.*



*Recommended format:*



*```*

*AC-001*



*AC-002*



*AC-003*

*```*



*Each criterion shall be:*



*- Observable.*

*- Testable.*

*- Binary.*

*- Independent.*



*---*



*# 13. Priority*



*Priority determines implementation order.*



*Recommended levels:*



*Critical*



*High*



*Medium*



*Low*



*Priority reflects business urgency.*



*---*



*# 14. Severity*



*Severity measures engineering impact.*



*Examples:*



*Critical*



*Major*



*Moderate*



*Minor*



*Trivial*



*Severity reflects technical impact rather than scheduling urgency.*



*---*



*# 15. Dependencies*



*Document dependencies including:*



*- Related Issues.*

*- Features.*

*- Architecture documents.*

*- APIs.*

*- External services.*

*- Infrastructure.*

*- AI workflows.*



*Dependencies shall remain explicit.*



*---*



*# 16. Implementation Notes*



*Provide guidance including:*



*- Technical considerations.*

*- Suggested approach.*

*- Constraints.*

*- Known limitations.*

*- Architectural implications.*



*Implementation Notes shall assist engineers without prescribing unnecessary details.*



*---*



*# 17. Testing Requirements*



*Specify required validation.*



*Examples:*



*- Unit Testing.*

*- Integration Testing.*

*- End-to-End Testing.*

*- Manual Validation.*

*- Regression Testing.*

*- AI Validation.*



*Testing shall confirm successful completion.*



*---*



*# 18. Definition of Done*



*The Issue is complete when:*



*- Acceptance Criteria are satisfied.*

*- Tests pass.*

*- Documentation is updated.*

*- Code review is approved.*

*- Governance compliance is verified.*

*- Deployment requirements are met.*



*Definition of Done standardizes completion.*



*---*



*# 19. AI Operational Context*



*Whenever applicable, specify:*



*- AI Agents involved.*

*- Required prompts.*

*- Context updates.*

*- Automation workflows.*

*- AI validation requirements.*



*AI context shall remain explicit.*



*---*

*```*

*Issue ID*



*DEV-231*



*Title*



*Implement Login Page*



*Type*



*Feature*



*Priority*



*High*

*Create the authentication interface following the Design System.*

*Authentication works.*



*Validation messages appear correctly.*



*Definition of Done*

*Code approved.*

*The example illustrates the expected level of detail.*



*---*



*# 21. AI Operational Contract*



*## Responsibilities*



*Every AI Agent shall:*



*- Read the complete Issue before implementation.*

*- Respect scope boundaries.*

*- Follow acceptance criteria.*

*- Preserve traceability.*

*- Recommend improvements when appropriate.*



*---*



*## Authorized Actions*



*Agents may:*



*- Break Issues into subtasks.*

*- Recommend implementation plans.*

*- Generate boilerplate code.*

*- Produce testing guidance.*

*- Suggest documentation updates.*



*---*



*## Restricted Actions*



*Agents shall not:*



*- Expand Issue scope autonomously.*

*- Ignore acceptance criteria.*

*- Modify priorities.*

*- Close Issues without validation.*

*- Bypass governance.*



*---*



*## Success Criteria*



*The Issue Template is successful when:*



*- Engineering work becomes predictable.*

*- AI Agents understand implementation context.*

*- Planning becomes consistent.*

*- Traceability improves.*

*- Delivery quality increases.*



*---*



*## Failure Conditions*



*The Issue Template fails when:*



*- Work begins without documentation.*

*- Scope is unclear.*

*- Acceptance Criteria are missing.*

*- Issues cannot be traced.*

*- AI Agents receive insufficient context.*



*---*



*## Escalation*



*Critical Issues affecting production systems, architecture, security, or governance shall be reviewed by the Project Owner before implementation.*



*---*



*# 22. Governance*



*The Issue Template governs every engineering work item within the AI-First engineering ecosystem.*



*Every production task shall be represented by an official Issue before implementation begins.*



*Future project management platforms, backlog managers, AI planning assistants, engineering orchestration systems, and repository automation tools shall remain compatible with the principles established herein.*
