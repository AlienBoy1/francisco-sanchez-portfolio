*# 1. Purpose*



*This document defines the Changelog process for the Francisco Sánchez Portfolio.*



*The Changelog serves as the authoritative chronological record of all significant technical changes introduced throughout the project's lifecycle.*



*Unlike Release Notes, which summarize publicly released versions, the Changelog records the complete engineering evolution of the project.*



*---*



*# 2. Objectives*



*The Changelog aims to:*



*- Maintain a complete history of project evolution.*

*- Improve engineering traceability.*

*- Support auditing and maintenance.*

*- Facilitate debugging and regression analysis.*

*- Document architectural evolution.*

*- Preserve historical context.*

*- Complement version control history.*



*---*



*# 3. Changelog Philosophy*



*Every meaningful change to the project shall be documented.*



*The Changelog is an engineering artifact intended to explain the evolution of the software beyond what can be inferred from individual Git commits.*



*Entries shall describe the intent and impact of changes rather than low-level implementation details.*



*---*



*# 4. Guiding Principles*



*The Changelog follows these principles.*



*- Chronological Accuracy.*

*- Traceability.*

*- Completeness.*

*- Clarity.*

*- Consistency.*

*- Engineering Transparency.*

*- Long-Term Maintainability.*



*Every recorded change shall adhere to these principles.*



*---*



*# 5. Scope*



*The Changelog records significant modifications across the project, including:*



*- New features.*

*- Architectural changes.*

*- Refactoring.*

*- Dependency updates.*

*- Security improvements.*

*- Performance optimizations.*

*- Bug fixes.*

*- Documentation updates.*

*- Build and deployment changes.*

*- Breaking changes.*



*Minor editorial corrections or insignificant formatting adjustments may be omitted.*



*---*



*# 6. Entry Classification*



*Each entry shall be categorized using standardized sections.*



*Representative categories include:*



*- Added*

*- Changed*

*- Deprecated*

*- Removed*

*- Fixed*

*- Security*

*- Performance*

*- Documentation*



*Consistent categorization improves readability and historical analysis.*



*---*



*# 7. Version Association*



*Every Changelog entry shall be associated with one of the following:*



*- A released version.*

*- A pre-release version.*

*- An unreleased development section.*



*Version identifiers shall follow Semantic Versioning.*



*Changes shall never be reassigned to different versions after publication.*



*---*



*# 8. Traceability*



*Every significant change should be traceable to supporting engineering artifacts where applicable.*



*Representative references include:*



*- Git commits.*

*- Pull Requests.*

*- Architecture Decision Records (ADRs).*

*- Product Requirements.*

*- Milestones.*

*- Issues or backlog items.*



*Traceability shall support future maintenance and auditing.*



*---*



*# 9. Maintenance*



*The Changelog shall be updated continuously throughout development.*



*Entries should be added as changes are completed rather than reconstructed retrospectively.*



*The Changelog shall remain synchronized with the actual project state.*



*---*



*# 10. Publication*



*The complete Changelog shall remain permanently available within the repository.*



*Historical entries shall not be removed.*



*If corrections are necessary, they shall be documented through additional entries rather than rewriting historical records.*



*---*



*# 11. Governance*



*The Changelog constitutes official engineering documentation.*



*Updates shall:*



*- Preserve chronological order.*

*- Maintain version consistency.*

*- Follow the approved classification system.*

*- Be reviewed before publication.*



*Major corrections require documented justification.*



*---*



*# 12. Compliance*



*All significant engineering changes shall be recorded according to this document.*



*Exceptions require documented approval by the Project Owner.*
